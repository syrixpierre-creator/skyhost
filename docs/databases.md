# Databases and storage

## Engines

PostgreSQL, MariaDB, MongoDB and Redis, each in its own container on the team network, with a dedicated volume,
resource limits from the plan and a generated password (encrypted at rest).

## Connecting a service

Connecting a database to a service adds its connection URL to the service as a variable resolved at deploy
time: `DATABASE_URL` for PostgreSQL and MariaDB, `MONGODB_URI` for MongoDB, `REDIS_URL` for Redis (the name can
be changed when connecting). Inside the team network the database answers on `<name>.internal`.

## Public access

Optional, per database: a TCP proxy publishes the database on `SKYHOST_DATABASE_PUBLIC_HOST` and a port from the
configured range. Prefer keeping databases private.

## Backups

- Scheduled backups (retention from the plan) and on-demand backups.
- Each backup is **verified**: it is restored into a temporary container and checked before being marked
  available.
- Backups are encrypted in the object storage; restoring replaces the current data after confirmation.
- Downloads are available to roles with the `database:backup` permission.

## Data browser

The dashboard can list tables/collections and run read-only queries. SQL queries run as a dedicated read-only
user; MongoDB and Redis commands are restricted to read operations.

## Credentials rotation

Rotating credentials changes the password, updates connected services and redeploys them.

## Buckets

Buckets expose the S3 API. Each bucket runs its own S3 gateway (VersityGW by default, `SKYHOST_BUCKET_IMAGE`)
with its own keys on the team network, reachable publicly at `https://s3-<id>.<base-domain>`. Buckets are
private by default; making one public allows anonymous reads only. Presigned URLs are generated by the API.
Writes are blocked when a bucket exceeds the plan quota.

## Volumes

Persistent volumes can be attached to services (mount path and size), with snapshots.
